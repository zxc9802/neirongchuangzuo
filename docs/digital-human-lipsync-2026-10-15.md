## 样片结论

用户确认 `D:/数字人周总.mp4` 是项目生成的成片。它有 241 帧，24 fps，画面 10.041667 秒，音频 10.080 秒。帧时间戳连续，两个轨道起点均为 0。这些格式数据本身不能证明逐字口型准确。

进一步在本机 GPU 上运行官方 SyncNet v2 权重，逐帧用 S3FD 检测唯一人脸，按官方裁切规则平滑人脸框并缩放到 224×224，画面采样到 25 fps，音频取 16 kHz 单声道 MFCC。比较相同内部画面窗口与前后最多 600 毫秒的音频特征，结果如下：

| 范围 | 最佳音频偏移 | 距离差置信值 |
| --- | --- | --- |
| 整体可比较窗口 | 0 毫秒 | 8.4092 |
| 前段（0–3 秒区间内） | 0 毫秒 | 7.2529 |
| 中段（3–6 秒区间内） | 0 毫秒 | 10.3412 |
| 后段（6–9 秒区间内） | 0 毫秒 | 7.0958 |

完整窗口的匹配距离为 7.8125。人为将音频特征延后或提前 200 毫秒后，测得偏移分别为 +200 和 -200 毫秒，未校正位置的距离分别升为 16.3497 和 15.9896。

这里的置信值不是百分比，也没有在本项目上标定“合格线”。25 fps 采样的步长为 40 毫秒；为避免边缘补零影响，比较窗口排除了边缘约 0.8 秒。结果支持“没有稳定的整体或分段延迟”，不支持给整条片子统一平移音轨；它不能证明每个汉字的唇形都准确，也不能否定用户对局部嘴型的观察。

`D:/老板音频.mp3` 的内容与该片实际配音不同，不能作为这条视频的原始驱动音轨来校准。本次没有定位到该片对应的线上任务及其供应商原始返回，所以不能将已复现的代码缺陷直接认定为这条样片的根因。

证据位于 `.data/digital-human-sample-20261015/syncnet/`：`check_sample.py`、`sample-syncnet.json`、`sample-features.pt`。模型与检测全在本机运行，样片没有上传到新服务。参考实现：[官方 SyncNet](https://github.com/joonson/syncnet_python)。

## 已修改的网站代码

1. 素材准备沿用最新 `main` 的画面轨道时长判断及末帧延长，补足完整配音时长。本次没有把已更新的流程改回旧版循环方式。
2. `services/digital-human/src/lib/engine/ffmpeg.ts`：没有显式分段时间轴时，拼接仍使用每段画面时长，避免容器中的音频尾部把下一段画面推迟。实际测试中第二段起点由 2.333008 秒恢复到 2.000 秒附近；原有按提交边界归一化的拼接路径继续保留。
3. `services/digital-human/src/lib/engine/lipsync-chunks.ts`：不足 0.4 秒的尾段合入前一段。原来 180.3 秒音频只安排 180 秒画面，现在覆盖全部音频。
4. `ffmpeg.ts`：最终换轨前检查实际画面长度与驱动配音长度，容忍正常帧舍入（至少 120 毫秒或两帧），超过容差即拒绝作为对口型结果交付。异常继续交由现有失败处理或基础配音降级流程处理，保留对应退款及恢复规则。
5. `services/digital-human/src/lib/server/public-data.ts`：向网页返回可理解的长度异常提示，不暴露内部路径。
6. `design/digital-human.js`：对口型成片预览提示核对逐字口型，避免将生成状态理解为人工验收结论。基础配音降级作品继续显示原有“未调整口型”提示。

这些改动修复了可重复的时间轴缺陷，没有更换口型引擎，也没有对样片强行添加固定延迟。部署状态以 GitHub 提交及部署平台为准。

## 逐字口型质量应如何继续改

推荐把网站扩展为“同一配音先生成 10–15 秒口型预览，确认后生成完整片子”。结果不合格时复用已生成的驱动配音，仅重做口型，方便比较方案，也避免每次 TTS 的不同停顿影响判断。

服务端保留任务的原始口型结果与驱动音轨，记录最终换轨前后的检测结果。自动检查分为长度/时间轴检查和音画对应评估：前者已加入；后者应使用正常样片及用户判定失败样片标定阈值，不能只凭一条样片的 SyncNet 分数直接自动放行。对于偏移稳定、置信度足够的结果才考虑自动校正；局部唇形错误应重生成，或通过同配音、同素材的对照测试选择引擎。

当前默认 B 方案实际使用 VEED。是否升级供应商模型，应先对同一片段做可比较的验收，再修改默认项；本次没有付费重跑供应商任务。
