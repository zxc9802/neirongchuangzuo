## 商家操作与结果

1. 首次保存门店名称、城市/商圈、地址、主营品类；其他信息可选，服务端按账号保存。
2. 一次选择 1—30 张 JPG/PNG/WebP 原图（单张最多 20MB、总计 400MB），确认图片及人物使用权。浏览器逐张纠正方向、缩放到最长边 2048 像素、压缩为 JPEG，每批最多 3 张；上传副本单张最多 8MB、总计最多 60MB，原文件保持不变。
3. 新工作流每批分析2张，用简洁结构记录食品、门店环境、服务/工作场景、质量和风险，并保留整个素材池。全部分析完成后才编排，不将某个文案方向的少量证据图片视为成品数量上限。
4. 默认9张，可选6—9张。全部照片分析后自动增加整组分镜规划节点，识别相同菜品的不同角度、真实食品主体以及不同制作/服务场景，保存主题、食品分组、每张来源、用途、主体焦点、机位和光线。至少3组不同食品主体时，9张优先7张食品、1张门头、1张环境；食品单一且有足够其他实拍时，自动使用最多3张食品，配合不同制作、出餐、门店和环境画面，同一食品组最多3张，不按食品照片文件数推断菜品丰富度。原图里整桌组合的不同可见食品可以分别取景。没有其他可用场景时才补足食品视角，不虚构新菜品或借用无关门店。服务端验证来源、张数、重复实景、食品分组与重复上限，规划失败时使用保留制作/服务素材的保守编排，不重放未知模型请求。页面展示简洁的套图编排，商家仍一键生成，无新增必填步骤。
5. 先识别主菜和完整承载餐具，高置信度定位时截取主盘并保留边距，不强行保留画面边缘偶然出现的其他盘菜；整桌套餐以主锅和原有食材种类为参考。生成和审核使用相同的主体参考，同时附带最多2张实际门店环境参考，匹配该店桌面、墙面、椅子、色系和空间尺度。允许变换机位、景别、光线和背景组织，调整同类食材的数量、摆盘和份量观感；不改变菜品与食材种类，不新增原图没有的食材。原图数量记录不作为生成验收硬限制，主菜或主锅完整，周边辅盘可自然局部入镜。逐张审核，不合格的已完成结果最多调整一次，再尝试其他可用食品；无法补齐整套则失败并释放积分。生图接口错误按下述备用模型规则处理，照片识别和审核的未知调用不重放。
6. 门店、环境和服务图纠正方向、提升亮度、色彩和清晰度，保留实景主体。统一输出1080×1440，不叠加标题、店名、序号或海报边框。非3:4实景保留完整画面，用原画面的柔焦延展补齐边缘。
7. 图片是主要交付物；配套文案通过事实和质量检查才附加，文案失败不会丢弃已经合格的套图，也不会返回空白文案文件。套图张数和积分按实际完整交付计，6张300分、9张450分（具体单价由全站积分配置决定）。
8. 需要确认的风险先展示实际成品预览，确认后结算并允许ZIP下载；只有当前账号可读取私有预览，不开放跨账号文件。提供单图和ZIP，图片保留3天。下载文案不包含内部审核JSON或风险注释。由商家人工发布。

旧接口和历史任务兼容自然美化、封面加字。新网页上传默认请求 autoGenerate:true 和 outputCount:6…9；新的宣传生成请求采用 workflow:store-gallery-v1。旧接口的张数/证据限制不作用于新套图流程。

任务可刷新恢复，完成后换方向会新建任务。分批上传草稿可重启续传；刷新后尚未上传部分需要重新选择同组原文件，已保存部分不重复上传。取消上传会释放任务名额；写入与到期清理共用文件屏障，晚到的文件仍由清理队列追踪。通过审核的单张成品逐张写入私有检查点，未完成整套时不开放下载；失败后商家点击「复用素材新建套图」，同一编排可继承未过期的已审核成品，继续处理未完成位置。改变张数或编排时不复用不匹配的成品。检查点同样3天到期清理。第一版不包含人物自动打码、手动排序、局部修图、独立重做封面、平台账号接入或自动发布。

## 生图备用模型

仅服务端配置 `FAL_IMAGE_KEY` 和 `FAL_IMAGE_MODEL=openai/gpt-image-2.5/sunburst/edit`；本地使用被Git忽略的 `.env.local`，生产由部署平台注入同名环境变量。与数字人/视频的 `VIDEO_FAL_KEY` 独立。没有备用密钥时保留原有单次生图行为。

通用单图、通用套图和餐饮食品重拍共用该机制：主接口首次调用失败后自动重试最多3次，四次均失败再提交一次fal。每次尝试有独立调用标识和终态，未知的旧尝试不会被改成成功或覆盖；备用结果带上相同提示词、事实原图、门店/风格参考和尺寸、画质，并保持安全检查。正常首轮成功不调用备用模型。图片内容质量不合格仍经过原有纠正/审核流程，不作为接口失败无限切换。

fal使用持久队列，接受后立即将供应商任务编号写入调用账本；状态或结果读取断连只重试GET，不重复提交生成。提交未获得确认时停为未知状态。服务重启时不重复POST，账本保留可核对的供应商任务编号；当前版本不自动接续重启前的供应商任务。文件下载仍使用受限下载器，客户端仅展示Max模型，不返回密钥和供应商模型标识。

供应商尝试数和商家积分分开：四次主模型尝试与一次fal均计入全站图片调用保护额度，轮询不计入；每日/每分钟调用限制、积分不足、存储失败和服务关闭不会绕过保护去发起备用请求。商家只按最终交付的图片结算一次积分，重试及切换不重复扣分，未交付的图片释放冻结积分。

## 文案质量与自动改写

推荐方向先确定真实亮点、目标顾客和消费场景，再形成具体消费理由。门头照片不会默认变成“到店前辨认入口”；纯看图、收藏外观或导航不能代替门店宣传主题。老板口吻可表达对可见氛围的审美和条件式邀约，但不伪装顾客，也不从店外水面推断店内江景餐位。

本地检查正文长度、长句与段落重复、内部分析口吻、过量认入口提醒、已确认店名是否出现，以及高度相似标题。模型再检查主题、消费理由、事实与隐私。完整已返回的初稿不合格时，带上原资料、最终图片、初稿和具体问题自动改写一次；二稿仍不合格则标记失败，不生成正式发布包、不扣商家正式额度。HTTP 200 响应中途断流也视为上游结果不确定，不自动重放。这些检查不保证内容会成为爆款。

推荐结果出现多类型素材却只有一个方向、各方向只有一两张候选并大量漏图、或主题完全重复时，基于已完整返回的推荐和具体问题最多重新规划一次；仍没有充分依据时不凑数量。补充候选必须来自可用真实照片，并说明核心、细节和场景用途；未采用图片须说明具体原因。正式选图必须保留核心证据，核心处理失败不能拿场景图代替后交付。

质量改造不增加首次操作步骤，不自动修改历史文案或旧任务推荐。尚未生成的旧任务可点「重新推荐」，复用已保存的照片分析和原门店资料，不重新上传或重新调用逐张识别；同请求标识幂等，不扣正式额度，但推荐调用照常计入共享预算。要应用新的照片筛选规则或更正门店资料，需要重新分析。已生成任务和原图到期任务不能重推荐。

## 数据、额度和状态

| 内容 | 存储和期限 |
| --- | --- |
| 门店资料 | PostgreSQL，长期保存，可由账号修改 |
| 正式额度账本 | PostgreSQL，长期保存，按 taskId 防重复扣额 |
| 任务、分析、方向、文案、风险、失败原因 | PostgreSQL，30 天 |
| 原图、处理图、封面、ZIP | 私有 COS 或持久化本地目录，3 天 |
| 供应商调用控制 | `.data/ai`，复用全站调用账本，须持久化 |

文件到期后禁止读取并排队清理；删除失败会重试，文字仍可查看。任务文字到期后任务不再可查询。资料和账本不随任务删除。换方向继承原图的原始到期时间，不延长原图保存期限。

商家额度默认每账号每天成功交付 20 套（`RESTAURANT_PACKAGE_DAILY_LIMIT`）；上传、分析、失败、自动重试不扣正式额度。生成时先预留，交付成功原子扣一次，失败释放。跨日预留继续占待交付额度，最终按北京时间交付日期计入；待确认图片到期会释放预留。

供应商调用次数与商家正式额度分开：Agent 和餐饮所有 Luna 调用共用全站每日 100 次、每分钟 10 次限制，已发出的失败请求也计入保护额度。新套图流程30张需要15次批量分析，再增加1次整组套图编排，对选中的不同食品主体各识别一次、每次食品重拍后审核一次，最后至多1次配套文案和1次文案审核；不额外调用旧流程的方向推荐。食品审核有明确偏差时最多纠正一次，再尝试同一食品组内的备用实拍；响应不确定的调用不重放。旧图文流程仍使用每批3张分析、模型推荐与文案改写。通用图片和食品重拍共用每日20次图片调用上限。这些是次数保护，不是人民币账单。

任务状态为 `uploading`、`analysing`、`awaiting_selection`、`awaiting_facts`、`generating`、`retrying`、`awaiting_confirmation`、`completed`、`failed`。审核状态为 `passed`、`passed_with_warning`、`blocked`。

## 服务端接口与代码

接口以 `/api/restaurant` 为前缀，生产统一验证已有登录会话；不能通过客户端传 userId 冒充账号。

| 方法与路径 | 用途 |
| --- | --- |
| GET `/status`、`/usage` | 模型配置状态、正式额度与内部调用预算 |
| GET / PUT `/profile` | 读取或保存本账号门店资料 |
| POST `/tasks` | `requestId`、`imageCount`、`rightsConfirmed` 创建上传草稿；套图另传 `autoGenerate:true`、`outputCount:6…9`；兼容旧 `images` 直接上传并分析 |
| POST `/tasks/:id/photos` | `startIndex`（0 起）、`images`（最多 3 张）；连续分批上传，相同批次幂等 |
| POST `/tasks/:id/analyse` | 照片齐全后开始分析；重复请求查询同一任务，不重复分析 |
| POST `/tasks/:id/recommend` | `requestId`；待选择或待补资料任务复用原分析重新推荐，同标识只调用一次 |
| POST `/tasks/:id/cancel-upload` | 取消尚未分析的分批上传草稿，释放任务名额并排队清理原图 |
| GET `/tasks?limit=12&cursor=...` | 历史任务分页 |
| GET `/tasks/:id` | 任务状态和结果 |
| POST `/tasks/:id/generate` | `directionId`、`imageMode`、`facts`、`acceptSparse`、`outputCount`；新套图使用 `workflow:store-gallery-v1`、`imageMode:promotional` |
| POST `/tasks/:id/confirm` | `confirmWarnings:true`，确认提示并交付 |
| POST `/tasks/:id/retry` | 明确失败且可重试的任务恢复；未知结果禁止原任务重发 |
| POST `/tasks/:id/fork` | 以新 `requestId` 创建换方向任务 |
| GET `/tasks/:id/files/:filename` | 检查账号、任务和期限后返回文件 |

前端为 `design/restaurant.js` 和 `restaurant.css`；流程服务为 `services/restaurant/server.mjs`，模型与提示词为 `model.mjs`、`prompts.mjs`，规则为 `rules.mjs`，持久化、媒体和图片处理为 `store.mjs`、`media.mjs`、`images.mjs`。

## 同事部署操作

2026-10-08 已核对线上 `/app/.data` 和 `/app/services/digital-human/.runtime` 的持久化挂载。后续更新保留既有挂载和数据库配置，并备份文件及 PostgreSQL；不要用新空卷替换现有数据卷。主分支推送会自动部署。

继续使用仓库根目录 Dockerfile，服务单实例运行，对外端口 8080。在 Zeabur 为应用分别挂载：

- `/app/.data`
- `/app/services/digital-human/.runtime`

新启动脚本会检查实际挂载，未挂载时拒绝启动。不要在容器里用 `PERSISTENT_STORAGE_CONFIRMED=1` 绕过检查；该开关只用于已确认目录持久化的裸机部署。部署前让正在执行的任务结束，优雅停止旧实例，再启动新实例，同一数据目录和餐饮数据库受独占锁保护，不支持滚动运行两个副本。

备份运行中目录可能带入旧运行锁。恢复备份前，**确认旧容器已经完全停止且没有第二个实例**；仅移除备份中的 `.data/ai/.runtime-control/lock` 和 `.data/ai/.runtime-control/takeover`（存在时），保留 `requests.json` 等账本和全部任务文件。容器异常退出后同样需要部署负责人确认旧实例退出，再处理旧锁；不同容器主机名的锁不会被系统擅自抢占。不要直接删除整个 `.runtime-control` 目录。

保留已有账号、域名、OpenLux 和数字人配置，新增可选项：

```dotenv
RESTAURANT_DATABASE_URL=
RESTAURANT_PACKAGE_DAILY_LIMIT=20
WORKSPACE_DATA_DIR=/app/.data
COS_SECRET_ID=
COS_SECRET_KEY=
COS_BUCKET=
COS_REGION=
```

`RESTAURANT_DATABASE_URL` 空时使用现有 `AUTH_DATABASE_URL`，在新注册账号库中自动创建独立 `restaurant_workspaces` 表（按账号保存 JSONB 状态），不修改内部账号库；数据库用户需要建表权限。不需要运行破坏性迁移。

COS 四项须全部配置或全部留空。可复用已有桶和服务端凭据，新对象放在 `restaurant/` 前缀并设私有 ACL；需要写入、读取、删除权限。确认桶策略没有向公众开放这个前缀。未配置 COS 时图片保存在 `.data/restaurant/media`，所以本地卷必须可靠持久化。不得在已有素材尚未到期时直接切换 COS / 本地存储，除非先迁移原对象。

Dockerfile 包含根依赖锁、Sharp、PG、FFlate、COS SDK 和 CJK 字体。非 Docker 的安装步骤：

```sh
npm ci
npm run setup:digital-human
npm run check
npm test
npm run check:digital-human
npm run build
npm start
```

生产变量由运行环境注入；生产不读取开发者根目录 `.env.local`。本地开发可在根 `.env.local` 设置餐饮连接串、COS、额度、数据目录，密钥和用户文件不入 Git。

部署后用自己的测试账号验证：登录 → 门店资料保存并刷新 → 上传有权使用的照片 → 推荐方向 → 生成 → 风险确认 → 单图及 ZIP 下载 → 刷新历史 → 检查额度只扣一次。再正常重启服务验证资料、任务与账本仍保留。不要用生产用户素材做删除或到期测试。
