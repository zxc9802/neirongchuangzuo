## 商家操作与结果

1. 首次保存门店名称、城市/商圈、地址、主营品类；其他信息可选，服务端按账号保存。
2. 一次选择 1—30 张 JPG/PNG/WebP 原图（单张最多 20MB、总计 400MB），确认图片及人物使用权。浏览器逐张纠正方向、缩放到最长边 2048 像素、压缩为 JPEG，每批最多 3 张；上传副本单张最多 8MB、总计最多 60MB，原文件保持不变。
3. 系统每批最多分析 3 张，逐张记录类型、对象、场景、质量、隐私和文字风险，再汇总推荐 1—4 个可靠方向。不强凑方向；全部不可用时停止。精确重复照片自动排除。
4. 商家选择方向和「自然美化 / 封面加字」，在当前页面设置最终 6—15 张成品，不能超过该方向可用照片数。少于 6 张时提供真实张数的简版，只有 1—2 张可用图时仍需确认继续。缺少核心事实时在当前页面补充或换方向，其他缺失描述避开。团购需要套餐、价格、使用条件。
5. 自动选图与排序，常规美化，生成 3 个标题、正文、5—8 个话题，再进行本地规则和模型检查。照片失败最多重试两次，然后尝试同方向备用照片；显式选择的最终张数无法补齐时整项失败、不扣正式生成额度。旧客户端未指定张数时保留自动重组规则。写作及审核会附带最多 3 张成功处理的真实照片，完整结构化分析仍涵盖所有最终选图。
6. 严重风险阻断；可确认提示先让商家确认，再正式交付和扣额。成功结果提供复制、单图下载和 ZIP 下载，由商家人工发布。

自然美化自动纠正方向，轻度调整亮度、色彩及清晰度，保留完整构图；不保证将每张横图强行裁成竖图。仅模型确认风险文字在边缘且裁剪能保留至少 75% 画面和全部主体时，进行安全裁剪；不能安全处理的照片排除。封面在第一张处理后照片下方扩展留白排字，不遮住主体，不额外产生一张虚构图片。

任务可刷新恢复，完成后换方向会新建任务。分批上传草稿可重启续传；刷新后尚未上传部分需要重新选择同组原文件，已保存部分不重复上传。取消上传会释放任务名额；写入与到期清理共用文件屏障，晚到的文件仍由清理队列追踪。模型响应不确定或服务异常中断时，不自动重发原任务的未知调用。第一版不包含人物自动打码、手动排序、局部修图、独立重做封面、平台账号接入或自动发布。

## 文案质量与自动改写

推荐方向先确定真实亮点、目标顾客和消费场景，再形成具体消费理由。门头照片不会默认变成“到店前辨认入口”；纯看图、收藏外观或导航不能代替门店宣传主题。老板口吻可表达对可见氛围的审美和条件式邀约，但不伪装顾客，也不从店外水面推断店内江景餐位。

本地检查正文长度、长句与段落重复、内部分析口吻、过量认入口提醒、已确认店名是否出现，以及高度相似标题。模型再检查主题、消费理由、事实与隐私。完整已返回的初稿不合格时，带上原资料、最终图片、初稿和具体问题自动改写一次；二稿仍不合格则标记失败，不生成正式发布包、不扣商家正式额度。HTTP 200 响应中途断流也视为上游结果不确定，不自动重放。这些检查不保证内容会成为爆款。

质量改造不增加商家操作步骤，不自动修改历史文案或旧任务推荐；新分析任务使用新选题标准。

## 数据、额度和状态

| 内容 | 存储和期限 |
| --- | --- |
| 门店资料 | PostgreSQL，长期保存，可由账号修改 |
| 正式额度账本 | PostgreSQL，长期保存，按 taskId 防重复扣额 |
| 任务、分析、方向、文案、风险、失败原因 | PostgreSQL，30 天 |
| 原图、处理图、封面、ZIP | 私有 COS 或持久化本地目录，3 天 |
| 供应商调用控制 | `.data/ai`，复用全站调用账本，须持久化 |

文件到期后禁止读取并排队清理；删除失败会重试，文字仍可查看。任务文字到期后任务不再可查询。资料和账本不随任务删除。换方向继承原图的原始到期时间，不延长原图保存期限。

商家额度默认每账号每天成功交付 20 套（`RESTAURANT_PACKAGE_DAILY_LIMIT`）；上传、分析、失败、自动重试不扣正式额度。生成时先预留，交付成功原子扣一次，失败释放。跨日预留继续占待交付额度，最终按北京时间交付日期计入；待确认图片到期会释放预留。

供应商调用次数与商家正式额度分开：Agent 和餐饮所有 Luna 调用共用全站每日 100 次、每分钟 10 次限制，已发出的失败请求也计入保护额度。30 张照片通常需要 10 次分析 + 1 次推荐 + 1 次文案 + 1 次审核；文案改写最多额外增加 1 次文案和 1 次审核调用，本地已阻断的初稿不再调用模型审核。明确尚未发送的每分钟限流可以排队等待，已发送且响应不确定的调用不重放。通用图片仍受每日 20 次上限控制。这些是次数保护，不是人民币账单。

任务状态为 `uploading`、`analysing`、`awaiting_selection`、`awaiting_facts`、`generating`、`retrying`、`awaiting_confirmation`、`completed`、`failed`。审核状态为 `passed`、`passed_with_warning`、`blocked`。

## 服务端接口与代码

接口以 `/api/restaurant` 为前缀，生产统一验证已有登录会话；不能通过客户端传 userId 冒充账号。

| 方法与路径 | 用途 |
| --- | --- |
| GET `/status`、`/usage` | 模型配置状态、正式额度与内部调用预算 |
| GET / PUT `/profile` | 读取或保存本账号门店资料 |
| POST `/tasks` | 新流程 `requestId`、`imageCount`、`rightsConfirmed` 创建上传草稿；兼容旧 `images` 直接上传并分析 |
| POST `/tasks/:id/photos` | `startIndex`（0 起）、`images`（最多 3 张）；连续分批上传，相同批次幂等 |
| POST `/tasks/:id/analyse` | 照片齐全后开始分析；重复请求查询同一任务，不重复分析 |
| POST `/tasks/:id/cancel-upload` | 取消尚未分析的分批上传草稿，释放任务名额并排队清理原图 |
| GET `/tasks?limit=12&cursor=...` | 历史任务分页 |
| GET `/tasks/:id` | 任务状态和结果 |
| POST `/tasks/:id/generate` | `directionId`、`imageMode`、`facts`、`acceptSparse`、`outputCount` |
| POST `/tasks/:id/confirm` | `confirmWarnings:true`，确认提示并交付 |
| POST `/tasks/:id/retry` | 明确失败且可重试的任务恢复；未知结果禁止原任务重发 |
| POST `/tasks/:id/fork` | 以新 `requestId` 创建换方向任务 |
| GET `/tasks/:id/files/:filename` | 检查账号、任务和期限后返回文件 |

前端为 `design/restaurant.js` 和 `restaurant.css`；流程服务为 `services/restaurant/server.mjs`，模型与提示词为 `model.mjs`、`prompts.mjs`，规则为 `rules.mjs`，持久化、媒体和图片处理为 `store.mjs`、`media.mjs`、`images.mjs`。

## 同事部署操作

2026-10-08 已核对线上 `/app/.data` 和 `/app/services/digital-human/.runtime` 的持久化挂载。后续更新保留既有挂载和数据库配置，并备份文件及 PostgreSQL；不要用新空卷替换现有数据卷。主分支推送会自动部署。

继续使用仓库根目录 Dockerfile，服务单实例运行，对外端口 8080。在 Zeabur 为应用分别挂载：

- `/app/.data`
- `/app/services/digital-human/.runtime`

新启动脚本会检查实际挂载，未挂载时拒绝启动。不要在容器里用 `PERSISTENT_STORAGE_CONFIRMED=1` 绕过检查；该开关只用于已确认目录持久化的裸机部署。部署前让正在执行的任务结束，优雅停止旧实例，再启动新实例，同一数据目录和餐饮数据库受独占锁保护，不支持滚动运行两个副本。

备份运行中目录可能带入旧运行锁。恢复备份前，**确认旧容器已经完全停止且没有第二个实例**；仅移除备份中的 `.data/ai/.runtime-control/lock` 和 `.data/ai/.runtime-control/takeover`（存在时），保留 `requests.json` 等账本和全部任务文件。容器异常退出后同样需要部署负责人确认旧实例退出，再处理旧锁；不同容器主机名的锁不会被系统擅自抢占。不要直接删除整个 `.runtime-control` 目录。

保留已有账号、域名、OpenLux 和数字人配置，新增可选项：

```dotenv
RESTAURANT_DATABASE_URL=
RESTAURANT_PACKAGE_DAILY_LIMIT=20
WORKSPACE_DATA_DIR=/app/.data
COS_SECRET_ID=
COS_SECRET_KEY=
COS_BUCKET=
COS_REGION=
```

`RESTAURANT_DATABASE_URL` 空时使用现有 `AUTH_DATABASE_URL`，在新注册账号库中自动创建独立 `restaurant_workspaces` 表（按账号保存 JSONB 状态），不修改内部账号库；数据库用户需要建表权限。不需要运行破坏性迁移。

COS 四项须全部配置或全部留空。可复用已有桶和服务端凭据，新对象放在 `restaurant/` 前缀并设私有 ACL；需要写入、读取、删除权限。确认桶策略没有向公众开放这个前缀。未配置 COS 时图片保存在 `.data/restaurant/media`，所以本地卷必须可靠持久化。不得在已有素材尚未到期时直接切换 COS / 本地存储，除非先迁移原对象。

Dockerfile 包含根依赖锁、Sharp、PG、FFlate、COS SDK 和 CJK 字体。非 Docker 的安装步骤：

```sh
npm ci
npm run setup:digital-human
npm run check
npm test
npm run check:digital-human
npm run build
npm start
```

生产变量由运行环境注入；生产不读取开发者根目录 `.env.local`。本地开发可在根 `.env.local` 设置餐饮连接串、COS、额度、数据目录，密钥和用户文件不入 Git。

部署后用自己的测试账号验证：登录 → 门店资料保存并刷新 → 上传有权使用的照片 → 推荐方向 → 生成 → 风险确认 → 单图及 ZIP 下载 → 刷新历史 → 检查额度只扣一次。再正常重启服务验证资料、任务与账本仍保留。不要用生产用户素材做删除或到期测试。
