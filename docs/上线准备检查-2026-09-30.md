# 网站上线准备检查

检查日期：2026-09-30。项目：店 AI · 实体生意宣传工作台。

**结论：当前可以本机体验和继续联调，尚不适合直接向多位商家正式开放。** Agent 和原图生图已接通；资产的成功成品保留 72 小时已实现。距离上线的主要工作是统一账号与数据权限、费用控制、补齐视频服务、建立生产部署及完成真实业务验收。

本次检查覆盖全部主导航页面、关键页面操作、前后端源码、自动测试、隔离生产构建、接口权限、任务与存储、依赖和部署配置。页面使用外置 Chrome，实际桌面视口 1920×991。没有访问公司服务器，没有提交代码或部署，没有新增付费生成；供应商真实成功记录沿用此前验收，本轮重新检查已有结果和调用实现。

## 2. 必须先处理的上线阻断

### A. 给整站接上统一账号，所有作品按用户或商家隔离

当前 `/api/ai/*` 不经过数字人的登录鉴权。无 Cookie 的本机请求能读取现有 5 个图片任务、任务创作要求及图片；更换任意 Cookie 得到同一列表。这是当前单人开发设计，不表示网站已经对公网泄露，但不能把它原样开放给多个商家。

需要为任务、原素材、成品、下载和请求去重记录增加用户/商家归属；提交、列表、详情、媒体读取都检查权限。前端补登录、退出、登录失效回跳，并处理固定浏览器缓存键导致的换号串历史问题。

**验收条件：** 未登录不能调用付费接口；账号 A 无法从列表、猜测 ID、下载链接或切换浏览器账号读到 B 的任何私有内容；过期会话能重新登录并回到原操作。

证据：[AI 审查 AI-01](release-audit-ai.md)、[前端审查 P0-2 / P1-1](release-audit-frontend.md)。

### B. 确认公司现有数字人、混剪如何复用

优先让新网站通过接口调用公司已经在运行的数字人和混剪服务。先拿到接口文档、测试账号、身份传递方式、积分规则、任务状态与下载规则，再做适配。

特别需要注意：导入的数字人代码固定使用 `_system/tasks.json`、`_system/avatars.json`、`_system/voices.json` 等云存储索引。**不能让新旧两个独立服务直接填同一个桶然后同时写入**，否则会共读写相同索引。若确实需要独立部署，必须独立存储，或者完整改造所有对象、索引和缓存的命名空间。

上游仍有固定产品标识、Cookie 与积分费率，不能只填密钥就认为与公司现站对接完成。

**验收条件：** 新站提交一个数字人/混剪任务，旧服务能识别正确用户和商家，正确预占与结算额度，返回结果；重复提交、失败、恢复都不会重复扣费；新站不会覆盖现站数据。

证据：[数字人审查](release-audit-avatar.md)。

### C. 补齐承诺上线的生成能力

AI 视频需要接供应商或公司现有视频能力；混剪需要接真实选片/剪辑/渲染服务。数字人本机状态接口显示配音、三种口型方案与媒体访问均未就绪，必须选择复用现网服务，或配置一条完整的生成链路。

**验收条件：** 每个对外开放模块各完成真实的“上传 → 提交 → 进度 → 成功/失败 → 下载 → 资产入库”流程，并核对实际成本。没有接好的能力不应保留成一个看起来随时可生成的承诺入口。

若希望尽快开始小范围试用，可先把 Agent、AI 图片和资产做成有账号和额度的版本；这是一种发布范围选择，并不等于四个生成模块全部完成。

### D. 建立费用与调用控制

当前 AI 后端只有整个进程最多 1 个图片任务、3 个对话请求的并发限制，没有按商家计算的额度、预算或调用账单。一个用户可以不断占用资源和消耗公司密钥。Agent 也没有服务端请求去重和断线结果查询。

需要设置账号/商家/系统三级限流与预算，保存供应商请求标识、用量、耗时和结算状态。明确成功结算、明确失败释放、结果不确定时待核对的规则；在读取大请求体前完成身份和请求数量限制。

**验收条件：** 超额度会在付费调用前被拦住；双击、刷新、断线、重试不会意外重复消费；后台能追踪某次费用属于哪个用户和任务。公司已有积分系统可复用，不要求另建一套充值系统。

### E. 建立真正的生产发布方式

根目录现在用开发预览启动，数字人使用 `next dev`。现有 Docker 只包含数字人子项目，没有新主站与 Agent/图片服务。图片后端拒绝非 localhost Host，代理把协议固定成 HTTP，因此不能只绑定域名就上线。

需要正式启动入口、统一 HTTPS 反向代理、正确的可信域名/代理配置、端口与路径规划、持久卷、进程守护、日志、健康检查与回滚。大文件上传、长任务超时、视频 Range 和任务事件流都需要在真实代理后验收。当前应用还缺请求级异常兜底：隔离测试中，一个畸形请求地址能终止主站进程，应修复为安全返回 400。

数字人 Docker 使用 Node 20；官方当前将其标为 EOL，应换成受支持且通过兼容性验证的 LTS。参见 [Node 官方版本状态](https://nodejs.org/en/about/previous-releases)。反向代理、环境变量及多实例注意事项参见 [Next 官方自托管指南](https://nextjs.org/docs/app/guides/self-hosting)。

**验收条件：** 在目标 Linux 环境从干净代码完成构建、启动和健康检查；真实域名下登录、上传、生成和下载成功；重启与更新不丢数据；旧网站继续正常运行；失败能恢复到上一版本。

## 3. 上线前还需补齐的可靠性与体验

| 优先级 | 已确认的问题 | 具体行动与验收 |
| --- | --- | --- |

| 中 | 商家资料、历史、收藏和草稿依赖当前浏览器 | 至少按账号隔离；重要资料按商家入库。原图不随草稿保存要继续明确提示，不应显示为已上传到长期素材库 |

| 中 | 尚无生产监控、备份恢复和管理员处置闭环的验收证据 | 告警覆盖失败率、供应商余额、积压、磁盘与清理；后台能查看任务/消费、定位失败、人工处理；演练恢复账号和任务记录，不恢复过期成品为可访问状态 |

素材有来源记录和 AI 示例标签，未发现足以认定整库不能使用的证据。正式发布前应补齐早期摄影来源存档，并沿用公司对用户上传图片、声音和形象授权、隐私告知、内容标识及发布前审核的要求；本次未做法律合规结论，也未查看公司现有材料。

现有历史文档存在状态滞后，例如《模型接入》仍有“未设置成品自动清理”的旧说明。正式交付时应统一用户说明和运维手册，以最新 72 小时规则为准。

## 5. 和公司同事对接时需要的信息

| 请同事提供 | 用途 |
| --- | --- |
| 现有数字人和混剪的 API 文档、测试地址与测试账号 | 判断能直接复用的接口，避免另做一套相同后台 |
| 登录、产品标识、用户/商家 ID、积分预留/结算/退款接口与回调规则 | 统一身份和收费，防止越权或重复扣费 |
| 当前部署方式、服务器系统、空余 CPU/内存/磁盘/带宽、现有端口 | 确定独立进程/容器布局和资源上限，避免影响现站 |
| 计划域名/子域名、HTTPS 入口与允许回调地址 | 解决路由、Cookie、可信代理及跨站问题 |
| 数据库和对象存储的现有归属/目录策略、可分配的独立空间 | 保证新旧数据不会互相覆盖，明确 72 小时清理范围 |
| 供应商与媒体可访问方案、预算、预期首批用户和日生成量 | 配置真实生成并确定限额、容量和压测目标 |
| 现站监控、备份、发布回滚和用户授权材料 | 接入已有运维与业务流程，减少重复建设 |

同一服务器可以共用网关、登录、积分和已有生成服务；新站代码、任务归属、持久目录与清理范围必须明确隔离。数据库实例可共享，但表/Schema/账号权限应有意规划；对象存储可由现有服务统一管理，不能把两套独立 JSON 写入器直接连到同一索引。

## 6. 推荐实施顺序及放行条件

1. **先确定复用契约与首发范围。** 获得数字人/混剪接口和登录/积分资料；列清本次真正开放的模块。
2. **完成统一身份、作品归属和调用额度。** 双账号隔离与重复提交验收通过后，才考虑向多人开放。
3. **补齐生成和任务可靠性。** 接服务、真实出片、费用对账、异常文件清理；修复进程异常退出；单实例或持久队列策略明确。
4. **搭建与现站隔离的测试环境。** 用正式构建、真实 HTTPS、持久卷、受支持运行版本、生产依赖；完成容器和数据库检查、备份与回滚。
5. **做上线验收并小范围开放。** 两账号、一次成功、一次失败、一次断线/重启、重复点击、下载、72 小时过期与原素材保留均验证；手机与弱网通过；记录成本、成功率、耗时和资源峰值，再扩大用户范围。

现在最值得推进的是第 1、2 步：先落实公司能力怎么接和账号怎么隔离，之后的服务器配置、存储与计费才有明确依据。
